# Database Architecture - Macro Overview

## The Big Picture: What Are We Building?

The MTG Card Swapper app is fundamentally about **enabling users to discover, negotiate, and complete card swaps with minimal friction 
and maximum privacy.**

The database tables are designed to support this workflow. Let's think about the user journey, then map it to tables.

---

## USER JOURNEY → DATABASE TABLES

### Step 1: **User Joins (Invite-Only Beta)**

**What happens:**
- You create an invite and send to alice@example.com
- Alice clicks link, signs up with email + password + username
- Alice's account is created

**Tables involved:**
- `invite_codes` — Stores the invite code (one-time token, 30-day validity)
  - Who invited her (you)
  - Her email (to validate when signup happens)
  - Status (pending → accepted when she signs up)
- `users` — Alice's account created here
  - Email, password hash, username
  - Optional location fields (hidden Phase 1, used Phase 2)
  - Reputation starts at 0

**Relationship:** invite_codes points to the user created after acceptance

---

### Step 2: **Users Add Cards to Their Collections**

**What happens:**
- Alice searches for "Black Lotus" in Scryfall
- She adds 2 copies: one Unused foil, one Played regular
- She adds notes: "slight bend on first one"
- Bob adds 10 cards to his collection

**Tables involved:**
- `cards` — One row per card in a user's collection
  - Links to Alice via user_id
  - Scryfall data (card name, set code, type, mana cost)
  - Condition (Unused/Played/Damaged), foil status, language
  - Quantity: 1 (each copy = separate row)
  - is_available: True (means they want to swap it)
  - Optional notes field

**Key insight:** Every user can have 100+ cards. Cards table is the "master inventory."

---

### Step 3: **Discover Other Users' Cards (Search)**

**What happens:**
- Alice searches: "I want Black Lotus"
- System queries: "Show all cards with name='Black Lotus' AND is_available=true"
- Results: "Bob has 1 Black Lotus (Unused), Carol has 3 Black Lotus (Played), Dave has 1 Black Lotus (Damaged)"
- Alice clicks "Bob" → sees Bob's entire card collection (all public Phase 1)

**Tables involved:**
- `cards` — Join with users table
  - Query: SELECT cards WHERE card_name LIKE 'Black Lotus' AND is_available=true
  - Then group by user to show "Bob has X, Carol has Y, Dave has Z"
  - Click user → show all user's cards

**Key insight:** Search is all in the cards & users tables. No new data created yet.

---

### Step 4: **Create an Offer (Negotiation Starts)**

**What happens:**
- Alice: "I want Bob's Black Lotus. I'll give you my 2x Llanowar Elves + 1x Forest"
- Alice creates Offer

**Tables involved:**
- `offers` — One row per swap negotiation between two users
  - initiator_user_id = Alice
  - target_user_id = Bob
  - status = "pending" (awaiting Bob's response)
  - expires_at = 7 days from now (auto-expire if Bob doesn't respond)
  - counteroffer_count = 0 (no negotiation yet)

- `offer_items` — Join table; shows which cards are in this offer
  - offer_id = this specific offer
  - card_id = Alice's Llanowar Elf #1 (first copy, offered by Alice)
  - item_type = "offered"
  
  - card_id = Alice's Llanowar Elf #2 (second copy, offered by Alice)
  - item_type = "offered"
  
  - card_id = Alice's Forest
  - item_type = "offered"
  
  - card_id = Bob's Black Lotus (the one Alice wants)
  - item_type = "requested"

**Key insight:** 
- One offer = one row in `offers`
- Many offer_items rows link to that offer (could be 1-10+ items)
- This cleanly separates negotiation (offers) from card inventory (cards)

---

### Step 5: **Negotiate (Counteroffer)**

**What happens:**
- Bob receives offer: "Alice wants my Black Lotus, offering 2x Elves + Forest"
- Bob thinks: "I'd rather have 3x Elves instead of Forest"
- Bob counteroffers: Same offer, but swaps Forest → Llanowar Elf

**Tables involved:**
- `offers` — Bob's counteroffer updates the SAME offer row
  - status stays "pending"
  - counteroffer_count = 1 (one round of negotiation)
  - expires_at is EXTENDED by 7 days (app logic updates this)
  - last_counteroffered_by = Bob (tracks whose turn it is, conceptually)

- `offer_items` — The offer items are REPLACED with new card selections
  - old items deleted (or status marked inactive, depending on implementation)
  - new items inserted: Alice now offers 3x Llanowar Elves (different request)
  - Bob's requested card (Black Lotus) might stay the same

**Alternative:** Instead of updating, this could create a new offer row with status="counteroffered", but we chose to keep it one offer 
row for simplicity.

**Max 4 counteroffers:** After 4 rounds of back-and-forth, offer auto-expires (prevents endless negotiation)

---

### Step 6: **Accept the Offer**

**What happens:**
- Alice receives Bob's counteroffer
- Alice: "OK, I'll do 3x Elves for your Black Lotus"
- Alice clicks Accept

**Tables involved:**
- `offers` — Alice's acceptance updates the same offer row
  - status = "accepted" (both agreed!)
  - accepted_at = NOW (timestamp of acceptance)
  - counteroffer_count = 1 (final round of negotiation)
  - expires_at no longer matters (offer accepted)

**Now a new table becomes relevant: swap_details**
- `swap_details` — Created when offer is accepted
  - offer_id = this accepted offer
  - swap_mode = NULL initially (will be decided next)
  - This unlocks messaging for Alice & Bob to coordinate

---

### Step 7: **Coordinate Swap Method (Messaging)**

**What happens:**
- Alice: "Great! How do we do this? I'm in Portland, OR. Can we meet?"
- Bob: "I'm in Seattle. Let's mail."
- Alice: "Sounds good! My address is..."
- Bob: "Mine is..."

**Tables involved:**
- `messages` — Chat thread on the offer
  - offer_id = this offer
  - sender_user_id = Alice (message 1), then Bob (message 2)
  - content = "Great! How do we do this?", then "I'm in Seattle. Let's mail.", etc.
  - created_at = timestamp of each message
  - Polling queries: GET /api/offers/{id}/messages?since= (fetch new messages every 2-5s)

- `swap_details` — Updated as they coordinate
  - swap_mode = "mail" (they decided on mail, not in-person)
  - mode_decided_at = NOW
  - shipping_from_address = Alice's address (Alice will ship)
  - shipping_to_address = Bob's address (Bob will receive)
  - carrier = "USPS" (chosen by Alice for outbound)
  - outbound_tracking_number = "1234567890" (Alice gets tracking)

---

### Step 8: **Complete Swap & Rate**

**What happens:**
- Alice ships cards to Bob (USPS tracking updates in messages if needed)
- Bob receives cards, marks swap complete
- Alice: "Great! I give you 5 stars ⭐⭐⭐⭐⭐"
- Bob: "Excellent service, 5 stars!"

**Tables involved:**
- `swap_details` — Updated when complete
  - swap_completed_at = NOW (Bob marks complete)
  - addresses_deleted_at = NOW (immediately delete addresses, privacy!)
  - After deletion trigger: shipping_from_address, shipping_to_address set to NULL
    (In practice, could be a scheduled job that runs after addresses_deleted_at timestamp)

- `ratings` — Alice and Bob each leave one
  - rater_user_id = Alice, rated_user_id = Bob
  - offer_id = this offer (for context: "I rated Bob on the Black Lotus swap")
  - rating_stars = 5
  - comment = "Great! Arrived quickly, cards as described."
  - Same for Bob rating Alice

- `users` — Alice and Bob's reputation updated
  - reputation_avg recalculated from their ratings table
  - total_swaps_completed incremented (Alice now has 1 swap, Bob now has 1 swap)

**Privacy win:** Addresses stored ONLY in swap_details, deleted immediately after completion. Users never store addresses on their 
profiles.

## TABLE PURPOSES & RELATIONSHIPS (MACRO VIEW)

### 1. **users** — The Identity Layer
**Purpose:** Store user accounts, authentication, profile data
- Core data: email, password, username, avatar
- Reputation tracking: reputation_avg (calculated from ratings), total_swaps_completed
- Privacy: location stored but hidden Phase 1
- Relationships: 
  - (1 user) → (many cards) — user owns cards
  - (1 user) → (many offers as initiator) — user creates offers
  - (1 user) → (many offers as target) — user receives offers
  - (1 user) → (many messages) — user sends messages
  - (1 user) → (many ratings as rater/rated) — user rates others, gets rated

---

### 2. **invite_codes** — The Access Control Layer
**Purpose:** Enforce invite-only beta, track community growth
- Stores invite tokens + metadata (who invited, when, status)
- Tracks conversions (pending → accepted when user signs up)
- Enables future community features (see who invited whom, build friend graph)
- Relationships:
  - inviter_user_id → users (who sent the invite)
  - accepted_user_id → users (who redeemed it)

---

### 3. **cards** — The Inventory Layer
**Purpose:** Master inventory of all cards users want to swap
- Denormalized Scryfall data (fast search, no API calls for every query)
- User-specific attributes: condition, foil, quantity, language, notes
- Availability status (is_available = do they want to swap?)
- Relationships:
  - user_id → users (who owns this card)
  - (many cards) ← (many offer_items) — cards appear in offers

---

### 4. **offers** — The Negotiation Layer (Core Business Logic)
**Purpose:** Manage swap negotiations from creation → acceptance → completion
- Status machine: pending → accepted → completed
- Expiration tracking (7 days, renewable on counteroffer)
- Counteroffer limit (max 4 rounds)
- Relationships:
  - initiator_user_id → users (who initiated)
  - target_user_id → users (who received)
  - (1 offer) → (many offer_items) — what cards are in this swap
  - (1 offer) → (1 swap_details) — post-acceptance coordination
  - (1 offer) → (many messages) — discussion thread
  - (1 offer) → (many ratings) — both users rate per offer

---

### 5. **offer_items** — The Line Item Layer
**Purpose:** Clean junction table; specifies which cards are offered vs requested in an offer
- Links cards to offers
- Separates "cards offered" from "cards requested" via item_type
- Allows many cards per offer (1-10+ items typical)
- Relationships:
  - offer_id → offers (which swap is this card part of?)
  - card_id → cards (which card in inventory?)

**Why separate table?** 
- Offers are at user-to-user level (negotiation)
- Cards are at inventory level (user collections)
- This table bridges them cleanly
- Allows flexible offer composition (add/remove cards during negotiation)

---

### 6. **swap_details** — The Coordination & Privacy Layer
**Purpose:** Post-acceptance logistics (how/where to swap) + privacy enforcement
- Swap mode: in-person (meet at location) vs mail (ship cards)
- In-person: proposed location + datetime + two-step confirmation
- Mail: addresses (stored ONLY here, deleted immediately post-completion)
- Privacy win: No address exposure until after offer accepted
- Relationships:
  - offer_id → offers (1:1) — one swap detail per offer

**Privacy enforcement:**
- Addresses visible ONLY after acceptance (not searchable, not indexed by default)
- Deleted immediately after swap marked complete (GDPR compliance)
- Never stored on user profiles

---

### 7. **messages** — The Communication Layer
**Purpose:** Real-time chat thread on offers (polling-based, 2-5s refresh)
- Messages tied to specific offer (private, only both parties can see)
- For coordinating swap details (location/time/address)
- System messages: "Offer accepted", "Swap completed" (automated)
- Phase 1: no read receipts (added Phase 2)
- Relationships:
  - offer_id → offers (which swap is this chat for?)
  - sender_user_id → users (who sent this message?)

---

### 8. **ratings** — The Reputation Layer
**Purpose:** Post-swap reviews, reputation system, community trust
- Only available after swap completed
- Each user rates the other (1-5 stars + optional comment)
- Linked to offer for context ("I rated Bob on the Black Lotus trade")
- Feeds user's reputation_avg (aggregate of all ratings)
- Relationships:
  - rater_user_id → users (who's rating?)
  - rated_user_id → users (who's being rated?)
  - offer_id → offers (which swap was this from?)

---

## DATA FLOW VISUALIZATION

```
User Registration Flow:
  invite_codes (invite sent)
      ↓
  users (signup)

Card Inventory:
  users → cards (user adds cards to collection)

Discovery:
  cards + users (search "Black Lotus", see who has it)

Negotiation Flow:
  users → offers (initiator creates offer)
  offers → offer_items (populate with cards)
  offers ← messages (discussion)
  offers → ratings (both rate after complete)

Coordination:
  offers → swap_details (after acceptance)
  swap_details (decide in-person vs mail + store addresses)
  swap_details ← messages (coordinate via chat)
  swap_details (delete addresses post-complete)

Reputation:
  ratings → users.reputation_avg (aggregate reviews)
```

## KEY DESIGN DECISIONS & WHY

### 1. **Separate offer_items Table (Not JSON)**
- Could store offered/requested cards as JSON in offers
- Chose separate table for:
  - Clean separation of concerns (offer negotiation vs card specifics)
  - Easy to add/remove items during negotiation
  - Indexed queries ("what cards are in this offer?")
  - Future: easy to track "Alice proposed X, Bob countered with Y"

### 2. **Denormalize Cards Data**
- Could store only scryfall_id and fetch names from API
- Chose to store card_name, set_code, etc. in cards for:
  - Fast search (no API calls per query)
  - Card data immutable (Magic cards never change)
  - Better UX (instant results in UI)
  - Trade-off: some duplication acceptable given use case

### 3. **Addresses Only in swap_details, Deleted Post-Swap**
- Could store full addresses on user profiles
- Chose swap_details + immediate deletion for:
  - Privacy first (addresses never public)
  - GDPR compliance (deleted by default)
  - Reduced liability (no long-term storage of sensitive data)
  - Better UX (users control when addresses shared)

### 4. **Invite Codes for Beta**
- Could use public signup immediately
- Chose invite codes for:
  - Community seeding (you control initial user base)
  - Spam/fraud prevention
  - Data: track "who invited whom" for future features
  - Sustainability: beta phase with friends before scale

### 5. **Reputation Calculated On-Read (Not Cached)**
- Could update reputation_avg via trigger after every rating
- Chose on-read calculation for:
  - Simplicity (fewer triggers, fewer edge cases)
  - Accuracy (always current, no stale cache)
  - Phase 1 scalability adequate (small user base)
  - Phase 2: can optimize if needed with materialized view

### 6. **max_counteroffers = 4**
- Could allow unlimited back-and-forth
- Chose 4 for:
  - Prevents endless negotiation loops
  - Encourages quick decisions
  - Phase 1 data: users can accept or move on
  - Balanced (2 exchanges = 4 status updates)

## QUERY PATTERNS (High-Level)

### "Who has Black Lotus?"
```sql
SELECT DISTINCT u.username, COUNT(*) as quantity
FROM users u
JOIN cards c ON u.id = c.user_id
WHERE c.card_name = 'Black Lotus' AND c.is_available = TRUE
GROUP BY u.id, u.username
ORDER BY u.reputation_avg DESC;
-- Returns: [Bob (5 stars, 1 copy), Carol (4 stars, 3 copies), Dave (3 stars, 1 copy)]
```

### "What's in Alice's pending offer to Bob?"
```sql
SELECT c.card_name, c.condition, oi.item_type
FROM offers o
JOIN offer_items oi ON o.id = oi.offer_id
JOIN cards c ON oi.card_id = c.id
WHERE o.initiator_user_id = alice_id AND o.target_user_id = bob_id AND o.status = 'pending';
-- Returns: [Llanowar Elf (used, offered), Forest (used, offered), Black Lotus (unused, requested)]
```

### "Messages in this offer?"
```sql
SELECT u.username, m.content, m.created_at
FROM messages m
JOIN users u ON m.sender_user_id = u.id
WHERE m.offer_id = offer_id
ORDER BY m.created_at ASC;
-- Returns: Chronological chat thread
```

### "Bob's reputation (average rating)"
```sql
SELECT AVG(r.rating_stars) as avg_rating, COUNT(*) as total_ratings
FROM ratings r
WHERE r.rated_user_id = bob_id;
-- Returns: [4.7 stars, 12 reviews]
```

## SUMMARY: The 8 Tables Work Together

1. **users** — identity & reputation hub (center)
2. **invite_codes** — gates access (entry point)
3. **cards** — primary inventory (searchable product)
4. **offers** — negotiation state machine (core business logic)
5. **offer_items** — line items per offer (bridges offers ↔ cards)
6. **swap_details** — post-acceptance logistics + privacy (sensitive data)
7. **messages** — negotiation communication (real-time chat)
8. **ratings** — post-swap feedback → feeds user reputation (reputation engine)

**The flow:** Users join (invite_codes → users) → Add cards (cards) → Search (cards + users) → Negotiate (offers + offer_items + messages) → Coordinate (swap_details) → Rate (ratings) → Build reputation (users.reputation_avg).

**Privacy architecture:** Addresses exist ONLY in swap_details, visible ONLY after acceptance, deleted IMMEDIATELY after completion.
