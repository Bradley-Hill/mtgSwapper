# MTG Card Swapper - Master Project Planning Document

## PROJECT VISION & GOALS

**Application:** Magic: The Gathering (MTG) Card Swapping Web App

**Core Purpose:** Enable MTG players to discover, negotiate, and exchange bulk cards with friends and acquaintances through in-person 
and mail-based swaps (no monetary transactions).

**Target Users:** MTG collectors and players looking to optimize their collections through non-monetary card exchanges.

**MVP Timeline:** Solo development, 20+ hours/week → Phase 1: 9-11 weeks (185-225 dev hours) + Phase 1.5: 2-3 weeks (40-50 hours)

**Launch Model:** Closed beta with friends (50-100 users, 4-8 weeks), then public Phase 1.5+ post-stabilization

---

## FINALIZED TECH STACK

### Frontend
- **Framework:** React + TypeScript + Vite
- **Routing:** React Router DOM v7 (BrowserRouter, nested routes, Outlet-based layouts)
- **State Management:** React Query/TanStack Query v5 (API state)
- **Styling:** SCSS with CSS Modules (one .module.scss per component, shared tokens in _variables.scss)
- **International:** i18next (EN+FR Phase 1, FR/ES/DE/IT/NL Phase 1.5)
- **Hosting:** Cloudflare Pages (auto-deploy from main branch)

### Backend
- **Framework:** Django + Python 3.10+
- **REST API:** Django REST Framework (DRF)
- **Real-time:** Polling 2-5s (not WebSocket) for simplicity
- **Database:** PostgreSQL (self-managed on Render)
- **Admin Panel:** Django built-in admin for moderation
- **Hosting:** Render (managed PostgreSQL + Python WSGI support)

### Database
- **Type:** PostgreSQL (managed on Render)
- **Schema:** 8 core tables (see mtg_database_schema_finalized.txt)
- **Reference:** Full schema + ER diagram in separate planning document

### Deployment
- **Backend:** Docker container on Render
- **Frontend:** Cloudflare Pages
- **Repository:** Public GitHub (building in public)
- **Environment:** docker-compose for local dev (optional), or Python venv + local PostgreSQL

### Core User Model (Invite-Only Beta)
- ✅ Invite-only sign-up (you send invite links to friends)
- ✅ Basic profile: username, optional city/region/country (all optional, privacy-protected)
- ✅ All cards visible to friend-group (no per-card privacy toggles Phase 1)
- ✅ Public reputation system (average rating + total swaps)

### Card Management (Discovery & Inventory)
- ✅ **Manual entry:** Add cards 1-by-1 via Scryfall search autocomplete
- ✅ **Bulk upload:** CSV import (name, set, quantity, condition)
- ⏳ **Image scanning:** Deferred to Sprint 8 (Tesseract OCR backend — see Sprint 8)
- ✅ **Card attributes:** Card name, set, condition (Unused/Played/Damaged), foil/non-foil, language, quantity
- ✅ **Card browse:** Search by name/set/color/type → see who has it → view user's full library
- ✅ **Scryfall integration:** Async API calls for card autocomplete & metadata

### Swap Workflow (Negotiation Engine)
- ✅ **Discovery:** Search card name → see all users who have it → browse their library
- ✅ **Basket creation:** Select cards from another user's library → propose swap
- ✅ **Offer lifecycle:** pending → accepted → completed (or declined/cancelled/expired)
- ✅ **Counteroffer support:** Target proposes different cards → initiator responds → loop (max 4 counteroffers)
- ✅ **7-day expiration:** Renewed by 7 days each counteroffer (prevents infinite negotiation)
- ✅ **Ownership validation:** Can only propose cards you own, request cards from target user

### Post-Acceptance Coordination (SwapDetails)
- ✅ **Mode decision:** Agree on in-person OR mail (decided post-acceptance, not upfront)
- ✅ **In-person meetup:** Propose location + datetime, two-step confirmation (both must agree)
- ✅ **Messaging hub:** Real-time chat (polling 2-5s) tied to offer → negotiate details
- ✅ **No mail phase 1:** In-person only for MVP (addresses safe to add later)

### Reputation & Ratings
- ✅ **Post-swap rating:** 1-5 stars + optional comment (max 500 chars)
- ✅ **Reputation calculation:** Average rating displayed on profile
- ✅ **Total swaps tracker:** Count of completed swaps per user
- ✅ **Rating visibility:** Public ratings history per user

### Internationalization (Phase 1)
- ✅ **Supported languages:** English (EN) + French (FR)
- ✅ **Scope:** UI strings + email templates (invites, password reset, notifications)
- ✅ **API errors:** English only Phase 1 (context visible in offer/message threads, less confusion)
- ✅ **Architecture:** i18next (frontend) + Django i18n (backend emails), extensible to Phase 1.5

### User Interface (Mobile-First)
- ✅ **Authentication:** Sign up via invite link, login
- ✅ **My Collection:** List cards, add/edit/delete, mark unavailable, bulk upload interface
- ✅ **Search & Browse:** Find cards by name → list users who have it → browse their library
- ✅ **Offer System:** Create offer from user's library → submit to target → track status
- ✅ **Offers Inbox:** View sent/received offers, filter by status (pending/accepted/completed)
- ✅ **Offer Detail:** See card details, messaging thread, counteroffer history
- ✅ **Messaging:** Real-time chat (polling) on each offer → negotiate swap mode + meetup details
- ✅ **User Profiles:** View any user's cards, reputation, ratings history
- ✅ **Rating UI:** Rate swap after completion, see rating confirmation

### Key Privacy Features
- ✅ **Address privacy:** Addresses ONLY stored in SwapDetails table (not user profile)
- ✅ **Address deletion:** Immediate deletion after swap marked complete (GDPR compliant)
- ✅ **No location exposure:** In-person meetup details negotiated in messages, not exposed to other users
- ✅ **Trust model:** Invite-only ensures initial friend-group only

## CORE WORKFLOW & USER JOURNEY

### Example: Alice Swaps with Bob

**1. Discovery (Alice finds Black Lotus)**
- Alice searches: "Black Lotus"
- System returns: "3 users have 'Black Lotus'" → [Bob, Carol, Dave]
- Alice clicks Bob → sees Bob's full card library (100+ cards)
- No location data shown yet

**2. Offer Creation (Alice proposes swap)**
- Alice browses Bob's library, selects cards to offer
- Alice adds to basket: [Llanowar Elves (x2), Forest (x1)]
- Alice selects cards she wants from Bob: [Black Lotus (x1)]
- Alice submits offer: "I give [Llanowar Elves x2, Forest x1] for [Black Lotus x1]"
- System creates offer, expires in 7 days
- Bob receives notification

**3. Counteroffer Negotiation (Bob responds)**
- Bob sees Alice's offer
- Instead of accepting, Bob counteroffers: "I'd rather have [Llanowar Elves x1 + Time Walk x1] instead"
- System updates offer → new 7-day timer starts
- Alice receives notification
- Alice accepts Bob's counteroffer (offer status = accepted)

**4. Post-Acceptance Coordination (Decide Mode)**
- Swap details unlocked
- Messaging thread opened
- Alice & Bob message: "How should we do this? Meet up or mail?"
- Alice: "I'm in Portland, can we meet Saturday 2pm?"
- Bob: "Perfect! Let's meet at Starbucks on 5th & Pike"
- Bob: "I confirm Saturday 2pm"
- Alice: "Confirmed!"
- System notes mode = "in_person", location confirmed

**5. Swap Completion & Rating**
- Sunday: Alice & Bob meet, exchange cards face-to-face
- Alice marks swap complete on the app
- Bob also confirms completion
- System deletes any addresses (not applicable for in-person, but follows protocol)
- Both rate each other: Alice gives Bob 5 stars "Great cards, perfect condition!"
- Bob gives Alice 5 stars "Quick, reliable trader!"
- Reputations updated on both profiles

## FINALIZED DECISIONS & RATIONALE

### ✅ Why React + TypeScript + Vite?
- React: Large ecosystem, component-driven, easy state management
- TypeScript: Type safety, better IDE support, fewer runtime errors
- Vite: Fast, modern dev experience (HMR), superior to Create React App
- Justification: Aligns with learning goals, widely-adopted, good for solo dev

### ✅ Why React Router DOM v7 (not TanStack Router)?
- Already installed and wired from Sprint 3 — no migration cost
- v7 has full nested route + Outlet support (Layout pattern works cleanly)
- Mature, battle-tested, huge community
- TanStack Router: excellent but adds complexity (file-based routes, type-safe params) not needed for MVP
- Justification: Simpler mental model, already in use, sufficient for Phase 1 route structure

### ✅ Why SCSS with CSS Modules (not TailwindCSS)?
- Tailwind removed during Sprint 3: utility classes obscure intent, hard to read, resist learning real CSS
- CSS Modules: zero class-name collisions, styles scoped to component, standard browser CSS
- SCSS: variables, nesting, partials — adds just enough power without a framework
- Shared design tokens in src/styles/_variables.scss (brand palette, spacing, radius, typography)
- Justification: Real CSS skills over framework dependency; codebase easier to reason about long-term

### ✅ Why Django + Python?
- Django: Batteries-included framework (ORM, auth, routing, admin, migrations)
- Python: Modern language, async/await support, good for learning
- DRF: Mature REST framework, widely adopted, excellent documentation
- Justification: Primary learning goal (Python/Django ecosystem), Django admin useful for moderation

### ✅ Why PostgreSQL (Self-Managed)?
- Relational model perfect for card matching queries (offers, ratings)
- Managed PostgreSQL on Render: Automatic backups, scaling, no ops overhead
- Justification: Learning database fundamentals + managed service takes ops burden off

### ✅ Why Polling (Not WebSocket via Channels)?
- Simpler architecture: Frontend polls every 2-5s for new messages
- No Channels complexity: Avoids WebSocket scaling, Redis, connection management
- Acceptable UX: 2-5s delay not noticeable for negotiation (not time-critical)
- Justification: MVP scope, trade-off between simplicity and real-time (can upgrade Phase 2)

### ✅ Why Invite-Only Phase 1?
- Smaller user base: Easier to moderate, test, iterate
- Quality over scale: Friend-group ensures higher engagement, trust
- Privacy-first: Closed beta = less abuse, cleaner data
- Justification: De-risk MVP, build with friends, scale post-stabilization

### ✅ Why Counteroffer Max 4 Rounds?
- Prevent infinite loops: After 4 counteroffers, offer auto-expires, forces decision
- Natural negotiation: 4 rounds usually sufficient for "I want this" ↔ "I'll give that instead"
- Clear boundary: Prevents analysis paralysis, encourages users to settle or move on
- Justification: Balance flexibility + user experience (not too restrictive)

### ✅ Why Full Addresses Deleted Immediately Post-Swap?
- Privacy-first: No permanent address storage (GDPR compliant)
- Trust: Users know data won't persist after swap completion
- Simplicity: No need for address backup/archive logic
- Justification: Aligns with privacy-sensitive design, reduces liability

### ✅ Why Internationalization in Phase 1 + 1.5?
- Phase 1 (EN+FR): UI + emails only, API errors in English (context visible in messages)
- Phase 1.5: Full multilingual (API errors + UI + emails in 6 languages)
- Modular approach: i18n built from day 1 (i18next + Django i18n), low cost to expand
- Justification: Balances launch speed (Phase 1) + quality (Phase 1.5), extensible architecture

### ✅ Why Card Conditions Simplified to 3 Values?
- Original plan: 6-level grading (Gem Mint, Near Mint, Light Play, Moderate Play, Heavy Play, Damaged)
- Simplified: Unused / Played / Damaged (easier for casual users, sufficient for MVP)
- Justification: Reduces decision paralysis, covers 90% of use cases, can expand Phase 2

### ✅ Why CSV/Decklist Bulk Upload + Image Scanning?
- Manual entry only = tedious for large collections
- Bulk upload: Natural for users importing existing collection (Moxfield/Arena export format)
- Image scanning: Modern UX, draws new users (can scan cards with phone camera)
- Combined: Users choose method that fits them (entry preference)
- Justification: Removes friction from high-volume card entry (essential for realistic MVP)
- Image scanning deferred to Sprint 8: Bulk import covers the immediate need. Camera UI requires
  React frontend to exist first. Tesseract (server-side Python) chosen over Google Cloud Vision
  to avoid paid API dependency — free, no usage limits, sufficient accuracy for MTG card fonts.

### ✅ Why Cloudflare Pages (Not Netlify/Vercel)?
- You already have Cloudflare domain infrastructure
- Zero-cost frontier for pet projects
- Native integration with Workers, KV, Analytics
- Justification: Leverage existing infrastructure, no new vendor lock-in

### ✅ Why Render (Not Railway)?
- You already use Render for PostgreSQL + backend
- Familiar infrastructure, connection strings, environment setup
- Managed PostgreSQL solid, Python support excellent
- Justification: Infrastructure familiarity, reduce cognitive overhead

## SPECIFIC DESIGN DECISIONS LOCKED IN

### User Model
- ✅ Invite-only signup (no public registration Phase 1)
- ✅ Optional location fields: city + region/state + country (all optional, privacy-protected)
- ✅ No formal friends system (all users see all cards in Phase 1)
- ✅ Username editable (users can change post-signup)
- ✅ Avatar URL stored (external URL, not file upload)

### Card Model
- ✅ Cards denormalized: card_name, set_code stored on card row (fast search, no API calls per query)
- ✅ Condition: 3-value enum (Unused, Played, Damaged)
- ✅ Language field: Track card language (English, French, Japanese, etc.)
- ✅ Quantity: INT field (multiple copies of same card = 1 row with quantity, not separate rows)
- ✅ is_available boolean: Mark cards swappable or kept
- ✅ All cards public to friend-group (no per-card privacy toggles)

### Offer Model
- ✅ Status values: pending → accepted → completed (also: declined, cancelled, expired)
- ✅ Counteroffer handled via offer_items table (old items deleted, new items inserted)
- ✅ Max counteroffer rounds: 4 (then auto-expires)
- ✅ Expiration: 7 days, renewed by 7 days on each counteroffer
- ✅ No quantity_in_offer field: Each card copy in offer = separate row (simplifies item tracking)

### Swap Details Model
- ✅ Created when offer accepted (unlocks messaging)
- ✅ Swap mode: decided post-acceptance via messaging negotiation (not upfront)
- ✅ In-person mode: proposed_location + proposed_datetime + two-step confirmation
- ✅ Mail mode: shipping addresses stored ONLY here, deleted immediately post-completion
- ✅ Cascade delete: If offer deleted, swap_details deleted too

### Messaging Model
- ✅ Real-time mechanism: Polling 2-5s (not WebSocket Channels)
- ✅ Messages visible only to offer participants (privacy)
- ✅ System messages: Automated events ("Offer accepted", "Swap completed")
- ✅ Read_at tracking: Deferred to Phase 2 (Phase 1: no read receipts)

### Offer Items Model
- ✅ Join table: Links offer ↔ card with item_type (offered vs requested)
- ✅ No quantity_in_offer: Each copy tracked as separate row (simplifies logic)
- ✅ UNIQUE constraint: (offer_id, card_id, item_type) prevents duplicates

### Ratings Model
- ✅ Tied to offer_id (why you rated them - for context)
- ✅ One rating per user per swap (UNIQUE constraint: rater_user_id, offer_id)
- ✅ Feeds users.reputation_avg (calculated on-read Phase 1)
- ✅ Audit_log table deferred to Phase 1.5

### Card Ownership Transfer on Swap Completion
- ✅ When both parties confirm a swap (status → completed), all OfferItem cards are
     re-assigned to their new owners:
     - item_type='offered' cards (initiator gave) → card.user = offer.target_user
     - item_type='requested' cards (target gave) → card.user = offer.initiator_user
- ✅ All transferred cards set to is_available=False (new owner decides when to re-list)
- ✅ Entire completion block (status flip + address deletion + card transfer) wrapped
     in transaction.atomic() — partial failure cannot leave DB in inconsistent state
- ✅ bulk_update() used for card re-assignment (single SQL UPDATE per batch)
- ⏳ PHASE 2: If initiator offered only SOME copies of a card (partial quantity), a
     card split mechanism would be needed. Phase 1 simplification: offering a card
     row = offering ALL copies. Full row transfers to new owner.

### Sprint 8 Detail: Card Ownership Transfer + Image Scanning (Tesseract OCR)

#### Part A — Card Ownership Transfer

**Why this was missed in Sprint 6:**
The `complete` action correctly handled offer status, timestamp, and address deletion,
but did not update the `cards` table. Cards remained registered to their original owners
even after the swap was confirmed. This is a correctness gap, not a UI gap — the data
model was simply not fully updated on completion.

**Design decisions:**
- `item_type='offered'` items: initiator's cards → reassigned to `offer.target_user`
- `item_type='requested'` items: target's cards → reassigned to `offer.initiator_user`
- All transferred cards set to `is_available=False` — new owner decides when to re-list
- Use `Card.objects.bulk_update(cards, ['user', 'is_available'])` for a single SQL UPDATE
  per batch (not N individual `card.save()` calls — important at scale)
- Entire completion block wrapped in `transaction.atomic()` — if any step fails (e.g.
  a card FK constraint), the DB rolls back completely. Without this, a crash between
  "status = completed" and "cards reassigned" would leave the offer completed but cards
  still belonging to the wrong users with no way to recover.

**Why transaction.atomic() matters here (learning note):**
Database transactions guarantee "all or nothing". Without `atomic()`, if your server
crashes mid-request, you can end up in a "partial success" state — the offer is marked
complete, the system message was sent, but card ownership was never updated. These
silent partial failures are among the hardest bugs to diagnose in production because
they leave no error trace. `atomic()` wraps the entire block so a failure at any point
triggers a full rollback to the pre-request state.

**Phase 2 note — partial quantity offers:**
Phase 1 simplification: offering a card row transfers ALL copies (the full Card row).
Phase 2 would need a "split" mechanism: if a Card row has quantity=3 and you offer 2,
create a new Card row with quantity=2 (the offered copies) and reduce the original to
quantity=1. Not needed for Phase 1 MVP.

#### Part A tasks
1. Wrap `complete` completion block in `transaction.atomic()`
2. Fetch OfferItems with `select_related('card')` for the completing offer
3. Re-assign offered cards to target_user, requested cards to initiator_user
4. `bulk_update` all transferred cards with new user + is_available=False
5. New test class: `OwnershipTransferTests`
   - Cards transfer to correct owners after dual confirmation
   - Cards set to is_available=False after transfer
   - Unrelated cards (same users, different offer) are untouched
   - Single confirmation does NOT trigger transfer (only on both confirmed)

### Sprint 8 Detail: Image Scanning (Tesseract OCR)

#### Why Tesseract (not TensorFlow, not Google Cloud Vision)
- **TensorFlow rejected:** General-purpose ML framework, not a card scanner. Would require
  collecting thousands of labelled card images, training a model, serving predictions.
  Months of ML engineering for a convenience feature.
- **Google Cloud Vision rejected:** Excellent accuracy but introduces a paid API dependency.
  1000 free units/month is not enough for active users. Wrong for a free community app.
- **Tesseract chosen:** Open-source OCR library. Free forever, no usage limits. Python wrapper
  (`pytesseract`) is a one-liner. MTG card names use a clear, consistent font — well-suited
  to OCR. Upgrade path to Google Cloud Vision exists post-revenue.

#### How it works
```
Phone camera (React, browser MediaDevices API)
    ↓
Capture image → POST /api/cards/scan/ (multipart/form-data)
    ↓
Backend: crop to top third of image (card name region)
    ↓
Tesseract: extract text from cropped region
    ↓
ScryfallService.search(extracted_text)  ← fuzzy match handles OCR imperfections
    ↓
Return: { card_name, set_name, language, scryfall_id, confidence }
    ↓
Frontend: add to staging list (user reviews before importing)
    ↓
User edits/removes misidentified cards
    ↓
POST /api/cards/bulk_import/  ← reuses existing endpoint
```

#### Language detection
Scryfall's multilingual search handles this automatically:
- French card scanned → OCR reads "Lotus Noir"
- Scryfall: GET /cards/search?q=!"Lotus Noir"+lang:fr → returns Black Lotus, lang: fr
- Stored as card_name: "Black Lotus", language: "French"
No extra logic needed — Scryfall does the work.

#### New endpoint
- **POST /api/cards/scan/**
  - Input: multipart/form-data with `image` field (JPEG/PNG)
  - Processing: PIL crop top 20% of image → pytesseract.image_to_string() → Scryfall fuzzy search
  - Output: `{ card_name, set_name, card_type, mana_cost, scryfall_id, confidence, raw_ocr_text }`
  - Errors: 400 if no text detected, 404 if Scryfall finds nothing
  - Auth: IsAuthenticated (same as all card endpoints)
  - No card is created — caller decides whether to add to staging list

#### New Python dependencies (Sprint 8)
- `pytesseract` — Python wrapper for Tesseract
- `Pillow` — Image preprocessing (crop, contrast boost, grayscale)
- System dependency: `tesseract-ocr` (apt package, added to Render build command)

#### React components needed (Sprint 8)
- `CameraCapture` — accesses device camera via `MediaDevices.getUserMedia()`
- `ScanStagingList` — list of scanned cards, editable before bulk import
- `ScanCardItem` — single row in staging list with edit/remove controls

#### Known limitations
- OCR accuracy degrades with: bad lighting, card held at angle, worn/damaged card text
- Preprocessing (contrast boost, deskew) mitigates this but doesn't eliminate it
- Staging list is the safety net — users review before committing
- Cards with non-Latin scripts (Japanese, Korean, Russian) will not OCR correctly via Tesseract;
  those users should use bulk import instead

security.

### Development Gotchas Learned

- **DRF nested router: `retrieve` vs `list` for 1:1 resources** — DRF's router maps `retrieve`
  to `GET /{pk}/` and `list` to `GET /`. For a resource that is 1:1 with its parent (e.g.
  SwapDetails — one per Offer, no separate pk), use `list` not `retrieve`. Using `retrieve`
  makes the router expect a pk segment in the URL (`/swap/{pk}/`), which is never what you
  want for a singleton sub-resource. Discovered: Sprint 6 `SwapDetailsViewSet`.

- **URL query strings silently corrupt ISO datetimes with timezone offsets** — Python's
  `datetime.isoformat()` for a UTC-aware datetime produces e.g. `2026-05-01T12:00:00+00:00`.
  In a URL query string, `+` is decoded as a space, so Django's `parse_datetime` receives a
  broken string and returns `None` — silently skipping the filter. Always wrap datetime values
  in `urllib.parse.quote()` before building query string parameters. Discovered: Sprint 6
  `?since=` filter in `MessageViewSet`.

- **`auto_now_add` timing in tests** — Two DB records created in rapid succession may receive
  identical (or near-identical) `auto_now_add` timestamps, making time-window tests flaky.
  Fix: use `.update()` (which bypasses `auto_now_add`) to explicitly back-date the "old"
  record after creation, then the "new" record's real timestamp is reliably later than the
  cutoff. Discovered: Sprint 6 `test_list_messages_since_filter`.
